# 추가 정보: 원본 대비 변경 내용

원본 저장소: `https://github.com/docker/getting-started-todo-app.git`

아래는 `git clone` 이후 이 저장소에 적용한 변경 내용입니다.

## 1. backend 폴더 교체

- 기존 Node.js(Express) 기반 `backend/`를 **2주차 과제 3**의 `getting-started-todo-app-FastAPI`에 있는 `backend/` 폴더로 교체했습니다.
- 교체 후 구성
  - FastAPI 앱: `backend/main.py`, `backend/src/` (`routes/`, `persistence/`, `models.py`)
  - 저장소 계층: SQLite, MySQL (`backend/src/persistence/`)
  - 테스트: `backend/spec/` (pytest)
  - 의존성/설정: `pyproject.toml`, `requirements.txt`, `requirements-dev.txt`, `uv.lock`, `pytest.ini`

## 2. client: JavaScript(JS/JSX)에서 TypeScript(TS/TSX)로 전환

- `client/src/`의 `.js`/`.jsx` 파일을 `.ts`/`.tsx`로 변경했습니다.
  - `App.tsx`, `main.tsx`, `components/AddNewItemForm.tsx`, `components/Greeting.tsx`, `components/ItemDisplay.tsx`, `components/TodoListCard.tsx`
  - 스타일: `components/ItemDisplay.scss`, `index.scss`
  - 타입 선언: `src/vite-env.d.ts`
- TypeScript 설정 파일
  - `tsconfig.json`, `tsconfig.app.json`(소스용), `tsconfig.node.json`(Vite 설정용)
  - `vite.config.ts` (기존 `vite.config.js`를 대체. 기존 파일은 `old-vite.config.js`로 남아 있음)

## 5. npm 보안 취약점 조치

`npm install` 직후 `npm audit`은 21건(high 19, moderate 1, low 1)을 보고했습니다.

- `npm audit fix`(semver 범위 내 수정)와 `sass` 업그레이드(1.70.0 → 1.108.2)로 **프로덕션 의존성 취약점은 0건**이 되었습니다.
- 남은 **10건(high)** 은 개발 도구 체인(`vite`, `tinyglobby`, `fdir`, `@typescript-eslint/*`)에 있는 `picomatch`(4.0.7 이하) 취약점입니다. 현재 패치된 `picomatch` 버전이 없어서 해결할 수 없습니다. 배포되는 산출물이나 런타임 의존성에는 포함되지 않습니다.
- `npm audit fix --force`는 메이저 버전을 올리므로 사용하지 않았습니다.

| 단계 | 기존 (Node) | 변경 (FastAPI) |
|---|---|---|
| `sqlite3-build` | `node-gyp`로 sqlite3 네이티브 빌드 | **삭제**. aiosqlite가 Python 표준 라이브러리 `sqlite3`를 쓰므로 컴파일이 필요 없음 |

### 6-3. 베이스 이미지 취약점 조치

IDE가 `node:22`와 `python:3.14-slim`에 취약점 경고를 표시하여, Docker Scout로 원인을 분석하고 조치했습니다.

| 베이스 | 조치 전 (Scout, fixable critical/high) | 조치 후 | 조치 내용 |
|---|---|---|---|
| `node:22` | 42H | `node:22-slim`으로 변경 | 전체 이미지에 들어 있던 PostgreSQL 15 라이브러리(High 32건, 수정 버전 있음)가 사라짐 |
| node npm | brace-expansion, pacote, sigstore, picomatch, ip-address (High) | `npm install -g npm@latest` | 이미지에 번들된 npm의 하위 패키지를 최신으로 갱신 |
| `python:3.14-slim` | 8H (msgpack, zlib, urllib3, setuptools, ...) | `apt-get upgrade` + `pip install --upgrade pip setuptools` | OS 패키지와 pip 번들 패키지를 최신으로 갱신 |

조치 후 베이스 이미지(`todo-base`, `todo-backend-base`)의 **수정 가능한 critical/high 취약점**은 다음과 같습니다.

- `todo-base` (node): 0건
- `todo-backend-base` (python): 1건(setuptools 70.3.0으로 보고됨). 그러나 실제 설치 버전은 84.2.1이고, setuptools를 제거해도 같은 보고가 나와 베이스 이미지 SBOM 메타데이터에서 온 것으로 보입니다.

- `compose.yaml`: backend 서비스의 watch 대상을 `backend/package.json`에서 `backend/requirements.txt`와 `backend/requirements-dev.txt`로 변경했습니다. 주석의 "Node.js server"도 "FastAPI server"로 고쳤습니다.

## 8. 알려진 한계

- `client/copy-build.js`는 빌드 결과를 `../backend/src/static`으로 복사합니다. 컨테이너 안에서는 `/usr/local/backend/src/static`에 복사되며, 최종 이미지는 `client-build` 단계의 `dist`를 사용하므로 영향은 없습니다.
- 베이스 이미지(`node:22`, `python:3.14-slim`)에 대해 IDE가 취약점 경고(critical 1, high 100+)를 표시했습니다. 이 경고의 세부 원인은 확인하지 않았고, 이번 작업에서는 베이스 이미지 버전을 바꾸지 않았습니다. 원인 분석과 베이스 이미지 갱신은 별도 작업으로 다루는 것이 좋습니다.
- 개발 도구 체인의 `picomatch` 취약점 10건은 업스트림에서 패치가 나오면 `npm update`로 해결할 수 있습니다.
- 베이스 이미지에 남은 취약점 중 **수정 버전이 없는 것(not fixed)** 은 해결할 수 없습니다.
  - node 베이스: `util-linux`, `zlib`, `pam`, `glibc`, `perl` (Debian, not fixed), `picomatch` 4.x (npm, not fixed)
  - python 베이스: `openssl` 3.5.7 (Debian, 6H, not fixed)
- `client-build` 중간 단계(최종 이미지에 포함되지 않음)에는 esbuild 바이너리의 Go 표준 라이브러리 `stdlib 1.23.x` 취약점(30H, 4C)이 있습니다. esbuild 0.25.x(최신 0.25.12로 갱신했으나 stdlib은 1.23.12로만 바뀌고 취약점은 그대로)에서는 해결되지 않습니다. 더 새로운 Go로 빌드된 esbuild가 필요하며, vite가 `^0.25`에 고정되어 있어 vite 메이저 업그레이드가 필요할 수 있습니다(이번에는 확인만 하고 하지 않았습니다).
- 이미지가 root 사용자로 실행됩니다(Scout 정책 경고). 취약점은 아니지만 별도로 비root 사용자를 추가하는 것을 검토할 수 있습니다.
- IDE 경고 수치(critical 1, high 100+)와 Docker Scout 수치는 집계 방식이 다르므로 그대로 일치하지 않을 수 있습니다.

## 10. 백엔드 신규 기능: 할 일 목록(Items) 필터링 API 구현

- **엔드포인트**: `GET /api/items` 및 `GET /items`
- **변경 내용**: `completed: Optional[bool] = None` 쿼리 파라미터 지원 추가 (`backend/src/routes/items.py`)
  - `GET /api/items?completed=true`: 완료(`completed == True`) 상태인 항목만 반환
  - `GET /api/items?completed=false`: 미완료(`completed == False`) 상태인 항목만 반환
  - 쿼리 파라미터 생략 시 전체 항목 반환
  - 잘못된 파라미터 전달 시 FastAPI/Pydantic 타입 검증에 의해 HTTP 422 Unprocessable Entity 자동 반환
- **단위 테스트 추가**: `backend/spec/routes/test_filterItems.py` (4개 테스트 케이스)
  - `test_get_items_filters_completed_true`: `completed=true` 필터링 검증
  - `test_get_items_filters_completed_false`: `completed=false` 필터링 검증
  - `test_get_items_without_filter_returns_all_items`: 쿼리 파라미터 미전달 시 전체 반환 검증
  - `test_get_items_invalid_completed_value_returns_422`: 부적절한 쿼리값 입력 시 422 상태코드 반환 검증

## 12. GitHub Actions CI/CD 파이프라인 구축 (`.github/workflows`)

저장소 협업 및 자동화 품질 관리를 위해 5개의 GitHub Actions 워크플로를 구축했습니다. (상세 설명: [.github_workflows.md](.github_workflows.md))

|---|---|---|

## 15. 환경별 Compose 파일 추가 및 Kubernetes(Katenary/Helm) 연동 지원

기존 로컬 개발 환경용 `compose.yaml` 외에, Kubernetes(Kind, GKE) 클러스터 배포 및 Helm 차트 변환(Katenary 도구 연동)을 위한 3개의 환경별 Compose 파일이 추가되었습니다.

### 15-1. 추가된 Compose 파일 구성

| 파일명 | 대상 환경 | 백엔드 이미지 (`backend.image`) | 주요 특징 |
|---|---|---|---|
| `compose-local_kind.yaml` | 로컬 Kind 클러스터 | `todo-backend:prod` (로컬 빌드, target: `final`) | - Dockerfile `final` 타깃으로 백엔드+프론트엔드 통합 운영 이미지 빌드<br>- 포트 3000 노출<br>- Katenary 및 Traefik Ingress 라우팅 레이블 적용 |
| `compose-github_kind.yaml` | GitHub Actions / Kind 배포 | `ghcr.io/cstpeace0191/ssu-cloud-computing/todo-backend:prod` | - GitHub Container Registry(GHCR)에 푸시된 프로덕션 이미지 사용<br>- 외부 레지스트리 기반 배포 환경 구성 |
| `compose-gcp_gke.yaml` | Google Cloud Platform GKE | `asia-northeast3-docker.pkg.dev/ssu-agent-vertex-509708/my-repo/todo-backend:prod` | - GCP Artifact Registry(서울 리전 `asia-northeast3`) 프로덕션 이미지 사용<br>- 클라우드 GKE 환경 배포에 맞춤 구성 |

### 15-2. Kubernetes/Helm 변환용 레이블 (`katenary.v3`) 설정

- **Proxy 서비스 무시 (`katenary.v3/ignore: "true"`)**:
  - Kubernetes 환경에서는 클러스터의 인그레스 컨트롤러(Ingress Controller)가 라우팅을 담당하므로, 개발용 Traefik 프록시 컨테이너는 Katenary를 통한 Helm 차트 변환 시 리소스 생성에서 제외합니다.
- **MySQL 호스트 동적 매핑 (`katenary.v3/map-env`)**:
  - `MYSQL_HOST: '{{ include "__APP__.fullname" . }}-mysql'` 설정을 적용하여, Helm 차트 릴리스 배포 시 릴리스 이름 기반의 Kubernetes Service DNS 주소가 백엔드 컨테이너 환경변수에 자동으로 주입되도록 구성했습니다.
- **Traefik Ingress 라우팅 규칙 정의**:
  - `web`(HTTP 80) 및 `websecure`(HTTPS 443) 엔트리포인트를 지원하며, `PathPrefix(/)` 규칙을 통해 백엔드 서비스(포트 3000)로 트래픽을 전달하도록 라우팅 규칙을 정의했습니다.

### 15-3. 로컬 실행 시 주의 사항 (포트 충돌)

- 로컬 Kind 클러스터(`my-k8s-control-plane`)가 실행 중인 상태에서는 해당 컨테이너가 호스트의 `80` 및 `443` 포트를 선점하고 있습니다.
- 따라서 기본 `compose.yaml`을 `docker compose -f compose.yaml up -d`로 기동할 경우, Traefik proxy 서비스에서 `Bind for 0.0.0.0:80 failed: port is already allocated` 오류가 발생할 수 있습니다.
- 이 경우 다음 중 하나로 조치합니다:
  1. Kind 컨테이너 일시 중지: `docker stop my-k8s-control-plane`
  2. `compose.yaml`의 proxy 포트 바인딩 변경: `80:80` → `8080:80` (접속: `http://localhost:8080`)
