# GitHub Actions 워크플로 종합 설명서 (.github/workflows)

이 문서는 저장소의 [.github/workflows](.github/workflows) 디렉터리에 위치한 모든 GitHub Actions 워크플로 파일들의 역할, 트리거 시점, 상세 작업 구성 및 실행 메커니즘을 정리한 문서입니다.

---

## 1. Push 시 모든 파일이 한꺼번에 실행되는가?

**결론: 아닙니다. 모두 한꺼번에 실행되지 않습니다.**

GitHub Actions의 각 워크플로는 상단의 **`on:`(트리거 설정)** 블록에 정의된 이벤트 및 브랜치/태그 조건과 일치할 때만 독립적으로 실행됩니다.

### 이벤트별 실행 매트릭스

| 이벤트 상황 | `ci.yml` | `pr-title.yml` | `publish.yml` | `promote.yml` | `release.yml` |
|---|:---:|:---:|:---:|:---:|:---:|
| **기능 브랜치 push** (`git push origin feat/**`) | **O** | X | X | X | X |
| **`main` 브랜치 push** (`git push origin main`) | **O** | X | **O** | X | X |
| **Pull Request 생성 / 제목 수정** | **O** | **O** | X | X | X |
| **버전 태그 push** (`git push origin v1.0.0`) | X | X | **O** | X | **O** |
| **Actions 탭에서 수동 실행** (`workflow_dispatch`) | **O** | X | **O** | **O** | X |

---

## 2. 워크플로 파일별 상세 설명

### 1) CI 검증 워크플로 — [.github/workflows/ci.yml](.github/workflows/ci.yml)

코드 변경 사항이 발생했을 때 백엔드 코드 품질/테스트, 프론트엔드 빌드/린트, Docker 이미지 패키징을 종합 검증합니다.

- **실행 시점 (`on:`)**:
  - `main` 브랜치를 대상으로 하는 PR이 열리거나 갱신될 때 (`pull_request`)
  - `main` 또는 `feat/**` 브랜치에 코드가 push될 때 (`push`)
  - Actions 탭에서 수동으로 실행할 때 (`workflow_dispatch`)
- **주요 설정**:
  - `concurrency`: 동일 브랜치/PR에 새 커밋이 push되면 이전 실행을 자동 취소하여 불필요한 러너 자원 소모 방지
  - `permissions: contents: read`: 저장소 코드 읽기 권한만 최소 부여
- **작업(job) 구성**:
  1. **`backend` (ruff + pytest)**:
     - Python 3.12 환경 설정 (pip 캐시 적용)
     - `pip install -r requirements-dev.txt`로 의존성 설치
     - `ruff check .`로 코드 스타일/린트 검사
     - `pytest`로 단위 테스트 실행 및 코드 커버리지 80% 이상 충족 여부 검사 (`--cov-fail-under=80`)
     - 요약 보고서를 `GITHUB_STEP_SUMMARY`에 출력하고, `junit.xml` 및 `coverage.xml`을 아티팩트로 업로드
     - 환경 변수: 러너 쓰기 권한 문제를 방지하기 위해 `SQLITE_DB_LOCATION: /tmp/todo-test.db` 지정
  2. **`client` (eslint + build)**:
     - Node.js 22 환경 설정 (npm 캐시 적용)
     - `npm ci --ignore-scripts`로 의존성 안전 설치
     - `npm run lint`로 ESLint 검사
     - `npm run build`로 프로덕션 빌드(HTML/CSS/JS 생성) 검증
  3. **`docker` (multi-stage build)**:
     - `backend`와 `client` 작업이 모두 성공해야 실행 (`needs: [backend, client]`)
     - Dockerfile의 `final` 타깃 멀티스테이지 빌드 수행 (로컬 이미지 `todo-app:ci`로 로드)
     - **스모크 테스트(Smoke Test)**: 빌드된 컨테이너를 구동한 후 최대 20초간 `/api/greeting` 엔드포인트 응답(HTTP 200)을 직접 검증

### 2) PR 제목 검사 워크플로 — [.github/workflows/pr-title.yml](.github/workflows/pr-title.yml)

Pull Request의 제목이 표준화된 커밋 규약(Conventional Commits)을 준수하는지 자동으로 검사합니다.

- **실행 시점 (`on:`)**:
  - PR이 생성되거나, 제목/본문이 수정되거나, 새 커밋이 추가되거나, 재오픈될 때 (`opened, edited, synchronize, reopened`)
  - **push 시점에는 동작하지 않으며, 오직 PR 이벤트에서만 실행됩니다.**
- **검사 규칙**:
  - 정규식 패턴: `^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\([a-z0-9-]+\))?!?: .{3,}`
  - 유효한 예: `feat(api): add filter by completed`, `fix(docker): copy vite config`
  - 무효한 예: `Update items.py`, `feat: x`, `Bump node...`
- **보안 모범 사례**:
  - 스크립트 인젝션 공격을 방지하기 위해 `${{ github.event.pull_request.title }}`를 shell 스크립트 문자열에 직접 삽입하지 않고, `env: TITLE: ...` 환경 변수로 안전하게 전달하여 검사합니다.

### 3) 컨테이너 이미지 배포 워크플로 — [.github/workflows/publish.yml](.github/workflows/publish.yml)

검증된 운영 코드를 Docker 이미지로 빌드하여 GitHub Container Registry(ghcr.io)에 배포하고, GitOps 저장소 승격을 트리거합니다.

- **실행 시점 (`on:`)**:
  - `main` 브랜치에 코드가 push될 때 (`push: branches: [main]`)
  - 버전 태그가 push될 때 (`push: tags: ["v*.*.*"]`)
  - Actions 탭에서 수동 실행할 때 (`workflow_dispatch`)
- **작업(job) 구성**:
  1. **`image` (빌드, 배포, 증명)**:
     - `ghcr.io`에 자동 로그인 (`GITHUB_TOKEN` 사용, `packages: write` 권한)
     - `docker/metadata-action`을 통해 커밋 SHA(`sha-<hash>`), 버전 태그(`v1.2.3`), `latest` 태그 자동 생성
     - 프로덕션 `final` 이미지 빌드 후 `ghcr.io/<소유자>/<저장소>`로 푸시
     - `actions/attest-build-provenance`를 사용해 소프트웨어 공급망 보안을 위한 OIDC 출처 증명(SLSA 증명서) 자동 첨부
  2. **`promote-dev` (GitOps dev 환경 승격)**:
     - `image` 작업이 완료된 후 `main` 브랜치 푸시 시에 실행
     - `promote.yml` 재사용 워크플로를 호출하여 dev 환경의 kustomize 이미지 태그 변경 PR을 오픈
     - 승격용 앱 ID 변수(`vars.PROMOTER_APP_ID`)가 설정되어 있을 때 안전하게 동작

### 4) 환경 승격 워크플로 — [.github/workflows/promote.yml](.github/workflows/promote.yml)

GitOps 환경(dev, stg, prod)의 형상 관리 저장소(`todo-app-config`)에 배포 이미지 태그를 갱신하는 PR을 생성하는 **재사용 가능 워크플로(Reusable Workflow)**입니다.

- **실행 시점 (`on:`)**:
  - `publish.yml`에서 호출될 때 (`workflow_call`)
  - 사람이 stg, prod 환경으로 배포하기 위해 수동 실행할 때 (`workflow_dispatch`)
- **입력값 및 시크릿**:
  - `target_env`: 배포 대상 환경 (`dev`, `stg`, `prod` 중 선택)
  - `image_tag`: 배포할 이미지의 40자리 Git 커밋 SHA
  - `PROMOTER_APP_KEY`: GitOps Config 저장소에 접근하기 위한 GitHub App 개인 키
- **동작 방식**:
  1. `actions/create-github-app-token`을 통해 Config 저장소(`todo-app-config`) 전용 쓰기 토큰 발급
  2. Config 저장소 체크아웃 후 `yq` CLI를 사용해 `overlays/<환경>/kustomization.yaml` 파일의 `newTag` 값을 갱신
  3. `todo-promoter[bot]` 이름으로 새 브랜치(`promote/<환경>-<해시>`) 생성 후 커밋 및 푸시
  4. GitHub CLI(`gh pr create`)를 사용하여 승격 PR을 오픈하고, `dev` 환경은 자동 병합(`--auto`) 설정

### 5) 릴리스 자동화 워크플로 — [.github/workflows/release.yml](.github/workflows/release.yml)

새로운 소프트웨어 버전 태그가 등록되었을 때 GitHub Release를 자동으로 생성하고 릴리스 노트를 발행합니다.

- **실행 시점 (`on:`)**:
  - `v1.0.0`과 같은 시맨틱 버저닝 태그가 push될 때만 동작 (`push: tags: ["v*.*.*"]`)
  - 일반 브랜치(`main`, `feat/**`) push 시에는 절대 실행되지 않습니다.
- **동작 방식**:
  - 이전 릴리스 태그와의 전체 커밋 이력을 비교하기 위해 `fetch-depth: 0`으로 전체 히스토리 체크아웃
  - `gh release create "$TAG" --generate-notes --verify-tag --title "$TAG"` 명령 실행
  - PR 제목 및 커밋 메시지를 바탕으로 변경 내역(Release Notes)을 자동 작성하여 릴리스 배포

## 3. 워크플로 종합 요약표

| 워크플로 파일 | 대상 이벤트 | 검사 / 수행 내용 | 산출물 / 배포 결과 |
|---|---|---|---|
| **ci.yml** | PR, main/feat push | ruff 린트, pytest(커버리지 80%+), eslint, client build, docker build & smoke test | 테스트 리포트 아티팩트 (`junit.xml`, `coverage.xml`) |
| **pr-title.yml** | PR 열림 / 수정 | Conventional Commits 규칙 준수 여부 정규식 검사 | PR 체크 통과/실패 표시 |
| **publish.yml** | main push, v* 태그 push | 최종 Docker 이미지 빌드 및 컨테이너 레지스트리 push, SLSA 서명 첨부, dev 승격 트리거 | `ghcr.io` 컨테이너 이미지, 출처 증명서 |
| **promote.yml** | workflow_call, 수동 | Config 저장소 kustomize 이미지 태그 갱신 및 배포 승격 PR 생성 | `todo-app-config` 저장소 승격 PR |
| **release.yml** | v* 태그 push | 이전 태그 대비 변경 사항 취합 및 GitHub Release 생성 | GitHub Releases 릴리스 노마크다운 발행 |
