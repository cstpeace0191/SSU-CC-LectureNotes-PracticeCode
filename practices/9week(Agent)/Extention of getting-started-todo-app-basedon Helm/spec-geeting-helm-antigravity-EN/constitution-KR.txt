# ============================================================================
# 프로젝트 헌장 (Constitution) - Getting Started Todo App
# ============================================================================

[핵심 요약]
코드 품질, 테스트 주도 접근법(Test-First), 웹 접근성, 성능에 대한 원칙 정의
(Define principles for code quality, test-first approach, accessibility, and performance)

----------------------------------------------------------------------------
핵심 원칙 (Core Principles)
----------------------------------------------------------------------------

I. 코드 품질 (Code Quality)
모든 프로덕션 및 인프라 코드는 엄격한 모듈화, 단일 책임 원칙, 클린 코드 표준을 준수해야 합니다.
- 병합(Merge) 전 모든 코드는 오류나 승인되지 않은 경고 없이 자동 린팅, 포맷팅, 정적 분석 검사를 통과해야 합니다.
- 함수, 컴포넌트 및 Helm 템플릿은 작고 조합 가능하며 중복 로직이 없어야 합니다 (DRY 원칙).
- 매직 넘버/값 및 환경별 설정값은 타입이 지정된 구성 파일이나 values.yaml에 외부화해야 하며, 소스 코드 또는 템플릿에 환경 매개변수를 하드코딩하는 것은 금지됩니다.
- 공개 인터페이스, 구성 키 및 비단순 알고리즘에는 간결하고 정확한 문서화(주석/문서)가 포함되어야 합니다.

* 근거: 일관된 코드 품질은 인지 부하를 줄이고, 환경 간 구성 편차(drift)를 방지하며, 장기적인 유지보수성을 보장합니다.

II. 테스트 주도 접근법 (Test-First Approach - 필수 준수)
모든 새로운 기능, 버그 수정, 차트/배포 변경 사항에 대해 테스트 주도 개발(TDD)이 의무화됩니다.
- 구현 코드를 작성하기 전에 자동화된 테스트(단위, 통합, 차트 검증/템플릿 테스트)를 먼저 작성하고 실패(Red)하는지 확인해야 합니다.
- Red-Green-Refactor 사이클을 엄격히 준수해야 합니다: 실패하는 테스트 작성(Red) -> 통과할 수 있는 최소한의 코드 구현(Green) -> 테스트를 통과한 상태에서 코드 정리(Refactor).
- 사전에 작성된 테스트 없이 동작 변경을 도입하는 풀 리퀘스트(PR)는 코드 리뷰에서 반려되어야 합니다.
- 모든 버그 수정은 수정 사항을 적용하기 전에 결함을 재현하는 회귀 테스트(Regression Test)부터 시작해야 합니다.

* 근거: 테스트를 먼저 작성하면 테스트 가능한 아키텍처가 강제되고, 사전 요구사항이 명확해지며, 코드가 프로덕션에 도달하기 전에 회귀 결함을 방지할 수 있습니다.

III. 웹 접근성 (Accessibility)
모든 사용자 대면 인터페이스는 기본적으로 포용적이고 접근 가능해야 하며, 최소 WCAG 2.1 Level AA 표준을 준수해야 합니다.
- UI 컴포넌트는 시맨틱 HTML 요소를 우선 사용해야 하며, 기본 시맨틱이 불충분한 경우에만 유효한 ARIA 속성을 사용해야 합니다.
- 모든 대화형 작업 흐름은 눈에 띄고 논리적인 포커스 상태를 제공해야 하며, 포커스 트랩(Focus trap) 없이 키보드 탐색만으로 조작 가능해야 합니다.
- 텍스트 및 대화형 요소는 WCAG AA 명도 대비 비율(일반 텍스트 4.5:1 이상, 대형 텍스트 및 UI 컴포넌트 3:1 이상)을 충족하거나 초과해야 합니다.
- 검증 워크플로에서 자동화된 접근성 검사(axe-core 또는 Lighthouse a11y)를 실행해야 하며, Critical 또는 Serious 위반이 0개여야 합니다.

* 근거: 접근성은 모든 사용자가 장애 여부나 보조 기술에 관계없이 애플리케이션을 인식하고 탐색하며 상호작용할 수 있도록 보장하는 기본 품질 요구사항입니다.

IV. 성능 (Performance)
애플리케이션 및 배포 산출물은 정의된 응답성, 자원 효율성 및 확장성 예산을 충족해야 합니다.
- 웹 인터페이스는 Core Web Vitals 기준을 달성해야 합니다: LCP(최대 콘텐츠 렌더링 시간) < 2.5초, INP(다음 페인트와의 상호작용) < 200ms, CLS(누적 레이아웃 이동) < 0.1.
- 백엔드 API 엔드포인트는 예상 부하 환경에서 표준 CRUD 작업에 대해 p95 응답 지연 시간을 200ms 미만으로 유지해야 합니다.
- 컨테이너 이미지와 Kubernetes/Helm 워크로드는 명시적인 CPU 및 메모리 requests/limits를 정의하고, 최소 크기의 기본 이미지를 사용하며, 불필요한 런타임 의존성을 배제해야 합니다.
- 핵심 경로 또는 번들 크기 예산에서 10%를 초과하는 성능 저하는 차단되거나 리뷰 중 명시적으로 승인받아야 합니다.

* 근거: 예측 가능한 응답 속도와 제한된 리소스 사용량은 사용자 만족도와 클러스터 운영 안정성에 직접적인 영향을 미칩니다.

----------------------------------------------------------------------------
품질 및 성능 제약 조건
----------------------------------------------------------------------------
- 정적 검증: 소스 파일 및 Helm 차트(helm lint, helm template)는 배포 또는 병합 전에 오류 없이 통과해야 합니다.
- 테스트 커버리지: 핵심 비즈니스 로직 및 API 라우트는 최소 80% 이상의 라인 및 브랜치 커버리지를 유지해야 합니다.
- 접근성 감사: UI 변경 사항은 작업 완료 전 키보드 탐색, 스크린 리더 시맨틱 및 명도 대비 요구사항에 대해 검증되어야 합니다.
- 리소스 위생: 무제한 쿼리, 메인 스레드 차단 작업, 증가하는 데이터셋에 대한 인덱스 없는 조회는 금지됩니다.
